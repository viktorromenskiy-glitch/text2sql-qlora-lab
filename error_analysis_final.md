# Error Analysis — оставшиеся 43 ошибки на финальном чекпоинте (0.785 EX)

## Общая картина

Из 200 примеров — 43 неверных (21.5%). Разбивка по типу:

| Категория | Количество | Доля |
|---|---|---|
| `wrong_result` (SQL валиден, логика неверна) | 39 | 91% |
| `execution_error` (SQL не выполнился) | 4 | 9% |

По сложности:

| Сложность | Ошибок |
|---|---|
| extra | 19 |
| medium | 13 |
| hard | 10 |
| easy | 1 |

**Главный вывод**: постобработка и связанные техники исчерпали свой
потенциал — 91% оставшихся ошибок это не механические/синтаксические
проблемы (которые мы уже почти полностью устранили), а **логические**
— модель генерирует полностью корректный, выполнимый SQL, который
просто не отвечает на вопрос так, как задумано.

## Детальный разбор — 10 примеров категории extra, wrong_result

### Паттерн 1 — лишний JOIN через `model_list` (4 из 10 просмотренных)

База `car_1` (car_makers/model_list/car_names/cars_data). Модель
**систематически** присоединяет `model_list`, хотя нужное поле (`Model`)
уже есть напрямую в `car_names` — то есть нужный JOIN короче, чем
модель предполагает.

```
Наш SQL:  model_list JOIN car_names JOIN cars_data
Gold:     car_names JOIN cars_data  (без model_list)
```

Пример:
- Вопрос: *«Find the model of the car whose weight is below the average weight»*
- Модель: `model_list JOIN car_names JOIN cars_data`
- Эталон: `CAR_NAMES JOIN CARS_DATA` — короче на одну таблицу

### Паттерн 2 — путаница `car_makers.FullName` vs `car_names.Make` (4 из 10)

Та же база. Два разных поля с похожим смыслом («производитель
автомобиля») в разных таблицах — модель непоследовательно выбирает
между коротким путём (`car_names.Make`) и длинным, правильным путём
через `car_makers.FullName` с полной цепочкой JOIN.

### Паттерн 3 — EXCEPT вместо NOT IN (2 из 10, другая база)

Для конструкции «есть X, но нет Y» модель предпочитает `SELECT ...
EXCEPT SELECT ...` (два одинаковых списка колонок), эталон использует
`WHERE ... AND id NOT IN (подзапрос)`. Семантически близко, но не
всегда эквивалентно (особенно при дублирующихся строках/составных
критериях).

## Итоговый вывод

Оставшаяся слабость — **не общая**, размытая проблема модели, а
**конкретная, воспроизводимая** трудность с **одной** особенно
запутанной схемой (`car_1`, 4 таблицы с пересекающимися по смыслу
полями) плюс один структурный паттерн (EXCEPT vs NOT IN). Это ценное,
конкретное наблюдение для портфолио — демонстрирует понимание, где
именно и почему остаются ошибки, не просто финальную метрику.

## Возможные, не реализованные пути дальнейшего улучшения

- Больше примеров именно схемы `car_1` в обучающей выборке (если бы
  делали data augmentation)
- Явное указание в промпте кратчайшего пути JOIN между таблицами
  (требует построения графа связей по foreign keys)
- Специализированная подсказка/пример именно для паттерна EXCEPT/NOT IN
