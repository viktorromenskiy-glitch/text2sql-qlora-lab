# Text-to-SQL: дообучение QLoRA на Qwen2.5-Coder-7B

Исследовательский эксперимент: дообучение открытой модели на 7 млрд параметров (QLoRA) для перевода вопросов на естественном языке в SQL на бенчмарке Spider. Задокументированы все прогоны, конфигурации и отрицательные результаты, включая технические ошибки, найденные и исправленные по пути, а не только итоговая метрика.

*English version: [README.md](./README.md) · Українська версія: [README.uk.md](./README.uk.md)*

**Коротко:** Qwen2.5-Coder-7B-Instruct, дообученная методом QLoRA (r=16, 3 эпохи на обучающей части Spider) плюс три техники на этапе вывода, даёт **78,5 % точности выполнения (157/200)** на первых 200 примерах dev-части Spider. Та же модель без дообучения даёт 69,5 % (139/200). Стек: PyTorch, Unsloth, QLoRA/PEFT, Google Colab.

Это эксперимент на одном публичном наборе данных, а не готовый продукт: точность на схеме базы данных конкретной компании нужно измерять отдельно.

## Результат

Все числа: точность выполнения (execution accuracy) на **первых 200 примерах dev-части Spider** (фиксированная подвыборка, не случайная), один прогон на конфигурацию, базы SQLite.

| Конфигурация | Точность выполнения |
|---|---|
| Базовая модель без дообучения (zero-shot) | 69,5 % (139/200) |
| Дообученный адаптер (r=16, 3 эпохи), без техник вывода | 73,5 % (147/200) |
| + постобработка SQL + поиск значений | 74,5 % (149/200) |
| + примеры значений в схеме (**итог**) | **78,5 % (157/200)** |

**+9,0 пункта к zero-shot** (на 18 примеров больше верных из 200).

Эффект отдельных техник на том же адаптере (те же 200 примеров):

| Добавленная техника | Точность | Изменение к варианту без техник (73,5 %) |
|---|---|---|
| Постобработка SQL | 74,0 % | +0,5 |
| Поиск значений | 74,0 % | +0,5 |
| Примеры значений в схеме | 77,0 % | +3,5 |
| Few-shot (поиск примеров) | 67,5 % | −6,0 |

Few-shot снизил точность и в итоговую конфигурацию не входит.

### Как читать эти числа

- Подвыборка небольшая: **разница в 1–3 примера (0,5–1,5 пункта) в пределах шума**. Явно за его пределами только крупные различия (примеры значений, few-shot).
- Техники и число эпох выбирались по результатам на этих же 200 примерах, поэтому 78,5 % скорее всего несколько завышены по сравнению с невиденными данными.
- Опубликованные результаты обычно считаются на полной dev-части (1 034 примера). Для справки: для Llama 3 8B с QLoRA там заявлено 77,2 %. Эти числа получены на разных подвыборках и **не являются сравнением на равных условиях**.
- Разметка тестовой части Spider локально недоступна, поэтому результат на тесте не приводится.
- Разброс между запусками: итоговая конфигурация показала 78.5% (157/200) 1 августа 2026. 2 августа в более новой программной и GPU-среде отдельный скрипт (`scripts/final_regression_and_errors.py`) снова нашёл 43 неверных ответа (78.5%), а та же команда `scripts/evaluate.py` с тем же адаптером дала 75.5% (151/200). Причина расхождения в 3 пункта не установлена, поэтому 78.5% следует читать как лучший наблюдавшийся результат, а не как устойчивую оценку.
- Сохранён только итоговый адаптер (r=16, 3 эпохи): SHA-256 его весов `1ab75e6db713820c7a3fb06dff0e0ddb5119f3e550eb1688e263849904118a0f`. Более ранние адаптеры из экспериментов с гиперпараметрами больше не хранятся, поэтому эти прогоны повторить нельзя.

## Почему это не «просто запуск туториала»

Чтобы получить итоговый результат, пришлось найти и исправить реальные технические ошибки: не косметические, а заметно влиявшие на результат:

- Функция потерь считалась по всему промпту (включая схему БД), а не только по целевому SQL: модель тратила обновления градиента на «копирование» контекста вместо обучения генерации SQL
- Отсутствовало расписание скорости обучения (разогрев + косинусный спад)
- При возобновлении обучения после обрыва сессии Colab номера чекпойнтов начинались с нуля и молча перезаписывали прежние, а диск Drive заполнялся; исправлено смещением номера шага и автоматической очисткой старых чекпойнтов
- Обработка кавычек в постобработке портила строковые литералы вроде `'USA'`, принимая их за выдуманные имена столбцов

Дополнительные заметки об ошибках: [`technical_lessons_learned.md`](./technical_lessons_learned.md) (на русском).

## Подход

1. **Эксперименты с гиперпараметрами**: число эпох обучения (1–4) и ранг LoRA (16 против 32) сравнивались на тех же 200 примерах; оставлен r=16 с 3 эпохами
2. **Сначала диагностика, потом исправление**: классификация типов ошибок на 200 примерах до написания любого кода коррекции
3. **Шесть техник на этапе вывода**, проверенных по отдельности и в комбинациях: постобработка SQL, целевой поиск значений в базе, примеры строк в схеме, few-shot-поиск, отсечение схемы (schema pruning), расширенная самокоррекция. Помогли не все; отрицательные результаты задокументированы наравне с положительными
4. **Анализ регрессий**: пошаговое сравнение по примерам, а не только итоговая метрика. Для итоговой конфигурации постобработка дала 0 регрессий и 3 улучшения (`scripts/final_regression_and_errors.py`); 43 ответа из 200 остаются неверными

Методология и выводы: [`implementation_priority_plan.md`](./implementation_priority_plan.md), [`error_analysis_final.md`](./error_analysis_final.md).

## Воспроизведение

См. [`RUNBOOK_milestone2.md`](./RUNBOOK_milestone2.md): пошаговые команды для Google Colab. `configs/eval_config.yaml` указывает на папку итогового адаптера.

```bash
python scripts/evaluate.py --model lora --postprocess --value-retrieval --sample-values
```

Примечание: оценка берёт первые 200 примеров dev в порядке файла (`seed=42` в коде на выбор примеров не влияет).
