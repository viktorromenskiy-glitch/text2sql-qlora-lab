# Text-to-SQL: донавчання QLoRA на Qwen2.5-Coder-7B

Дослідницький експеримент: донавчання відкритої моделі на 7 млрд параметрів (QLoRA) для перекладу питань природною мовою в SQL на бенчмарку Spider. Задокументовано всі прогони, конфігурації та негативні результати, включно з технічними помилками, знайденими й виправленими по дорозі, а не лише фінальну метрику.

*English version: [README.md](./README.md) · Русская версия: [README.ru.md](./README.ru.md)*

**Коротко:** Qwen2.5-Coder-7B-Instruct, донавчена методом QLoRA (r=16, 3 епохи на навчальній частині Spider) плюс три техніки на етапі виводу, дає **78,5 % точності виконання (157/200)** на перших 200 прикладах dev-частини Spider. Та сама модель без донавчання дає 69,5 % (139/200). Стек: PyTorch, Unsloth, QLoRA/PEFT, Google Colab.

Це експеримент на одному публічному наборі даних, а не готовий продукт: точність на схемі бази даних конкретної компанії потрібно вимірювати окремо.

## Результат

Усі числа: точність виконання (execution accuracy) на **перших 200 прикладах dev-частини Spider** (фіксована підвибірка, не випадкова), один прогон на конфігурацію, бази SQLite.

| Конфігурація | Точність виконання |
|---|---|
| Базова модель без донавчання (zero-shot) | 69,5 % (139/200) |
| Донавчений адаптер (r=16, 3 епохи), без технік виводу | 73,5 % (147/200) |
| + постобробка SQL + пошук значень | 74,5 % (149/200) |
| + приклади значень у схемі (**підсумок**) | **78,5 % (157/200)** |

**+9,0 пункта до zero-shot** (на 18 прикладів більше правильних із 200).

Ефект окремих технік на тому самому адаптері (ті самі 200 прикладів):

| Додана техніка | Точність | Зміна відносно варіанта без технік (73,5 %) |
|---|---|---|
| Постобробка SQL | 74,0 % | +0,5 |
| Пошук значень | 74,0 % | +0,5 |
| Приклади значень у схемі | 77,0 % | +3,5 |
| Few-shot (пошук прикладів) | 67,5 % | −6,0 |

Few-shot знизив точність і до підсумкової конфігурації не входить.

### Як читати ці числа

- Підвибірка невелика: **різниця в 1–3 приклади (0,5–1,5 пункта) у межах шуму**. Явно поза його межами лише великі відмінності (приклади значень, few-shot).
- Техніки та кількість епох обиралися за результатами на цих самих 200 прикладах, тому 78,5 % імовірно дещо завищені порівняно з небаченими даними.
- Опубліковані результати зазвичай рахуються на повній dev-частині (1 034 приклади). Для довідки: для Llama 3 8B із QLoRA там заявлено 77,2 %. Ці числа отримано на різних підвибірках, і вони **не є порівнянням на рівних умовах**.
- Розмітка тестової частини Spider локально недоступна, тому результат на тесті не наводиться.
- Збережено лише підсумковий адаптер (r=16, 3 епохи): SHA-256 його ваг `1ab75e6db713820c7a3fb06dff0e0ddb5119f3e550eb1688e263849904118a0f`. Ранніші адаптери з експериментів із гіперпараметрами більше не зберігаються, тому ці прогони повторити неможливо.

## Чому це не «просто запуск туторіалу»

Щоб отримати підсумковий результат, довелося знайти й виправити реальні технічні помилки: не косметичні, а такі, що помітно впливали на результат:

- Функція втрат рахувалася по всьому промпту (включно зі схемою БД), а не лише по цільовому SQL: модель витрачала оновлення градієнта на «копіювання» контексту замість навчання генерації SQL
- Бракувало розкладу швидкості навчання (розігрів + косинусний спад)
- Під час відновлення навчання після обриву сесії Colab номери чекпойнтів починалися з нуля й мовчки перезаписували попередні, а диск Drive заповнювався; виправлено зсувом номера кроку та автоматичним очищенням старих чекпойнтів
- Обробка лапок у постобробці псувала рядкові літерали на кшталт `'USA'`, сприймаючи їх за вигадані назви стовпців

Додаткові нотатки про помилки: [`technical_lessons_learned.md`](./technical_lessons_learned.md) (російською).

## Підхід

1. **Експерименти з гіперпараметрами**: кількість епох навчання (1–4) і ранг LoRA (16 проти 32) порівнювалися на тих самих 200 прикладах; залишено r=16 з 3 епохами
2. **Спершу діагностика, потім виправлення**: класифікація типів помилок на 200 прикладах до написання будь-якого коду корекції
3. **Шість технік на етапі виводу**, перевірених окремо й у комбінаціях: постобробка SQL, цільовий пошук значень у базі, приклади рядків у схемі, few-shot-пошук, відсікання схеми (schema pruning), розширена самокорекція. Допомогли не всі; негативні результати задокументовано нарівні з позитивними
4. **Аналіз регресій**: покрокове порівняння за прикладами, а не лише підсумкова метрика. Для підсумкової конфігурації постобробка дала 0 регресій і 3 покращення (`scripts/final_regression_and_errors.py`); 43 відповіді з 200 залишаються неправильними

Методологія та висновки: [`implementation_priority_plan.md`](./implementation_priority_plan.md), [`error_analysis_final.md`](./error_analysis_final.md).
