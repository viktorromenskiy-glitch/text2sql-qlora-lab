# План реализации — приоритет по (ожидаемое улучшение) / (стоимость)

Основано на двух независимых анализах (мой + Gemini) и уже полученных
собственных результатах. Все проценты ниже — из литературы, **не наши
подтверждённые цифры** — реальный эффект на нашей модели может
отличаться, возможно существенно. Использовать как ориентир для
приоритизации, не как гарантию.

## Приоритет 1 — Левенштейн + примеры значений (наш готовый код)

- **Стоимость**: ~0 — код уже написан и протестирован локально
  (`sql_postprocess.py`, `prompt_formatter.py`), нужно только запустить
  на LoRA-модели (раньше проверяли только на baseline)
- **Ожидаемый прирост**: не оценён количественно в источниках, но
  описан как «заметный» для Левенштейна отдельно
- **Дешёвая проверка**: уже есть скрипт-шаблон
  (`evaluate_cheap_improvements.py`), адаптировать под `load_lora_model`
- **Делать первым** — нет причин откладывать нулевую по стоимости
  проверку

## Приоритет 2 — Value Retrieval (находка Gemini)

- **Суть**: искать слова из вопроса среди реальных значений в текстовых
  колонках БД (`'London'` vs «лондонский»), подсказывать модели найденное
  совпадение в промпте
- **Стоимость**: средняя — простой поиск по строкам (можно начать с
  точного/нечёткого совпадения, без сложного BM25/FAISS для дешёвой
  версии)
- **Ожидаемый прирост**: +3-5% EX (источник: DAIL-SQL/CodeS-related
  практика, не наша проверка)
- **Дешёвая проверка**: 50 примеров, вручную/regex выделить строковые
  константы в вопросах, проверить долю ошибок именно от несовпадения
  значений
- **Почему приоритет 2, не 1**: требует написания нового кода (поиск по
  БД), но целится в конкретный, правдоподобный механизм ошибок — выше
  ожидаемая польза, чем у Приоритета 1

## Приоритет 3 — Schema Pruning (находка Gemini)

- **Суть**: убирать нерелевантные таблицы/колонки из промпта перед
  генерацией (не путать с нашим «примеры значений» — здесь наоборот,
  сокращаем, а не добавляем)
- **Стоимость**: высокая — нужен классификатор/retriever для отбора
  релевантных таблиц
- **Ожидаемый прирост**: +5-8% EX (самая высокая оценка среди всех
  находок, источник: CodeS/CHESS)
- **Дешёвая проверка**: 30 самых «тяжёлых» схем (10+ таблиц), вручную
  обрезать до реально нужных, сравнить точность
- **Почему не первый приоритет несмотря на высокую оценку**: заметно
  дороже в реализации, чем 1-2 — проверяем после более дешёвых вариантов

## Приоритет 4 — Few-shot примеры (оба анализа, с оговоркой)

- **Стоимость**: средняя — нужен семантический поиск похожих примеров
  (embeddings + kNN)
- **Ожидаемый прирост**: +2-4% EX (DAIL-SQL), **но**: другой источник
  (Llama 3 8B работа) сообщает «неубедительный» эффект поверх SFT —
  противоречивые данные
- **Дешёвая проверка**: обязательна перед полной реализацией именно
  из-за противоречия источников — 50 примеров, Sentence-Transformers
  для поиска похожих

## Приоритет 5 — Продвинутая самокоррекция (N-кандидатов + голосование)

- **Важно**: это НЕ то же самое, что уже протестированный нами вариант
  (1 попытка, 0 эффекта) — версия Gemini генерирует 5 кандидатов и
  выбирает большинством голосов
- **Стоимость**: высокая — 5x инференса на пример, заметно медленнее
- **Ожидаемый прирост**: +4-7% EX (Gemini, DAIL-SQL-related)
- **Дешёвая проверка**: 50 сложных/ошибочных примеров, цикл
  генерация→ошибка→фикс

## Не приоритет сейчас — полный агентный pipeline (MAC-SQL-стиль)

Multi-agent декомпозиция (Selector/Decomposer/Refiner) — самый высокий
потолок в литературе (85%+), но несопоставимо более сложная
реализация. Рассматривать только если Приоритеты 1-4 в сумме не дадут
достаточного результата.

## Честная оговорка про суммарный эффект

Сам Gemini предупредил: цифры из разных работ «могут суммироваться
нелинейно». Не рассчитывать на простое сложение процентов (например,
не ждать 70%+22%=92%) — реальный кумулятивный эффект неизвестен до
проверки.
