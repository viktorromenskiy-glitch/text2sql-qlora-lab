# План реализации — v2, после дискуссии Claude ↔ Gemini

Первая версия плана (см. историю) опиралась на ориентиры (CodeS 79-82%,
MAC-SQL >85%), которые при проверке первоисточников оказались
неприменимы к нашей ситуации напрямую: CodeS требует отдельного
дорогостоящего пре-трейнинга (21.5 ГБ корпуса), которого у нас нет;
MAC-SQL >85% достигается только с GPT-4 как backbone — на открытой
7B-модели (их же собственный тест) результат заметно ниже. Это
подтверждено прямыми цитатами из обеих статей.

**Реалистичный ориентир для нашего класса модели** (Qwen2.5-Coder-7B,
только QLoRA + inference-time техники, без масштабного претрейна) —
работа ROUTE: **+5% абсолютного прироста** на Spider dev. Обновлённый
прогноз Gemini (после дискуссии) — суммарно **+3.5% — +5.5%**, то есть
итоговая точность около **73.5% — 75.5%** EX. Это и есть честный,
дважды проверенный потолок ожиданий.

## Итоговая архитектура — однопроходный pipeline, не агентная система

```
[Вопрос + БД]
     │
     ▼
1. Value Linking (BM25/regex по текстовым колонкам)
     │
     ▼
2. Light Schema Filtering (только для баз с >8 таблиц)
     │
     ▼
3. Dynamic Few-Shot (kNN, 2-3 примера)
     │
     ▼
4. LLM-генерация (наша дообученная Qwen2.5-Coder-7B)
     │
     ▼
5. Deterministic Fix (1 итерация коррекции по ошибке SQLite)
     │
     ▼
[Финальный SQL]
```

## Приоритет — по пересмотренным, консервативным оценкам

| № | Техника | Реалистичный прирост | Сложность | Дешёвая проверка |
|---|---|---|---|---|
| 1 | Deterministic Execution Guard (1 коррекция) | +1.5–2.5% | Низкая | 2 часа — прогнать через sqlite3, разделить ошибки на 2 типа |
| 2 | Value Retrieval / Cell Linking | +1.0–2.0% | Низкая | 3 часа — проверить на примерах с 0 строк результата |
| 3 | Dynamic Few-Shot (kNN, 3 примера) | +1.0–1.5% | Средняя | Embeddings + топ-3 похожих примера на 50 dev-примерах |
| 4 | Light Schema Filter | +0.5–1.5% | Средняя | Только на базах >8 таблиц — вручную на 10 примерах |

**Суммарно (не аддитивно гарантированно)**: +3.5–5.5% → итог ~73.5–75.5% EX

## Наш уже готовый код (Левенштейн + примеры значений) — куда встал в новом плане

Левенштейн-коррекция имён таблиц концептуально близка к пункту 1
(Deterministic Execution Guard) — можно использовать как один из
механизмов коррекции. «Примеры значений в схеме» — не то же самое, что
Value Linking (пункт 2) Gemini — тот предлагает **точечный** поиск
конкретных упомянутых в вопросе значений, не общие примеры по 2-3 на
таблицу. Наш код остаётся полезным, но не заменяет пункт 2 напрямую.

## Порядок реализации — от дешёвого/подтверждённого к дорогому

1. Deterministic Execution Guard — используя уже готовый Левенштейн-код
   как часть механизма коррекции
2. Value Retrieval — новый код, целится в конкретный, подтверждённый
   механизм ошибок (несовпадение значений)
3. Few-shot — только после 1-2, с честной проверкой на 50 примерах
4. Schema Filter — последний, самый дорогой, эффект ожидается только на
   сложных базах
