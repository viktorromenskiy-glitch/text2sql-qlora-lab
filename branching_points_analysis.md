# Точки ветвления — теоретический обзор и план дешёвой проверки

Цель этого документа — не просто повторить чужой результат fine-tuning
на Spider, а показать **систематическое исследование альтернатив**,
каждая проверена дёшево, прежде чем вкладываться в дорогую (по
GPU-времени) реализацию. Источник ориентиров — реальная литература,
найденная веб-поиском (см. `technical_lessons_learned.md`, раздел 19).

## Принцип дешёвой проверки — общий для всех веток

Не тестировать на полных 200 примерах сразу. Вместо этого:
1. Взять **маленькую, целевую подвыборку** (20-60 примеров) — либо
   случайную, либо специально отобранную (например, только те, где
   текущая модель уже ошиблась — из `results_lora.json`)
2. Прогнать **и без техники, и с ней** на этой подвыборке
3. Если разница обнадёживает — тогда уже полный прогон на 200

Это на порядок дешевле по времени инференса, чем сразу гнать 200
примеров на каждую гипотезу.

---

## Ветка 1 — Продолжить дообучение дольше (уже в процессе)

**Гипотеза**: 1500 шагов (~0.86 эпохи) — недообучение, не переобучение
(см. раздел 19 `technical_lessons_learned.md`). Реальный найденный
ориентир — **Qwen2.5-Coder-7B давал 81.7% EX** в отдельной научной
работе (SPS-SQL).

**Статус**: уже выполняется (продолжение с `checkpoint-1500`, ещё
+2000 шагов, итого ≈3500 ≈ 2 эпохи).

**Дешёвая проверка не нужна** — это и есть сам эксперимент, результат
увидим по завершении.

---

## Ветка 2 — Execution-guided самокоррекция (приоритет №1, готовлю код сейчас)

**Идея**: если сгенерированный SQL не выполняется (синтаксическая
ошибка) или возвращает пустой результат — не сдаваться сразу, а дать
модели ещё одну попытку с сообщением об ошибке в промпте.

**Почему приоритет**: не требует переобучения, только `evaluate.py`;
дёшево по GPU (максимум одна дополнительная генерация на пример);
несколько независимых работ подтверждают пользу этой техники (LitE-SQL,
ZAS-SQL, SQL-PaLM).

**Дешёвая проверка**: взять из `results_lora.json` (или из уже
случившегося прогона) конкретно те примеры, где `correct=False` —
особенно `parse_failure=True` или невыполнимый SQL. Прогнать **только
их** (не все 200) с добавленной самокоррекцией — если существенная доля
переходит в `correct=True`, эффект подтверждён дёшево, без полного
повторного прогона.

---

## Ветка 3 — Few-shot примеры в промпте (SPS-SQL-подход)

**Идея**: рядом со схемой добавлять в промпт 1-2 похожих, уже решённых
примера из обучающей выборки (по сходству схемы/темы вопроса).

**Почему может сработать вместе с уже дообученной моделью**: SPS-SQL
получила 81.7% на Qwen2.5-Coder-7B именно **комбинацией** few-shot +
модель этого же класса — не факт, что это взаимоисключающе с нашим
fine-tuning, возможно, эффекты складываются.

**Сложность**: нужен простой поиск похожих примеров (например, по
пересечению имён таблиц/столбцов в вопросе — не нужен полноценный
retrieval с эмбеддингами, это было бы избыточно для дешёвой проверки).

**Дешёвая проверка**: подвыборка 30 примеров (по 7-8 на каждый уровень
сложности) → сравнить EX с few-shot и без, на уже дообученной модели.
Инференс, не обучение — быстро.

---

## Ветка 4 — Декомпозиция для сложных вопросов (DIN-SQL-подход)

**Идея**: для вопросов, которые выглядят сложными (много таблиц,
вложенные условия), — сначала попросить модель разбить на подзадачи,
затем собрать финальный SQL, вместо прямой генерации за один шаг.

**Обоснование из литературы**: *«декомпозиция работает лучше именно на
сложных вопросах, простой few-shot достаточен для лёгких»* (DIN-SQL) —
прямо целится в нашу самую слабую точку (hard/extra: 0.54/0.40 у LoRA).

**Сложность**: заметно выше двух предыдущих — нужна двухшаговая
генерация, промежуточный парсинг, больше точек отказа.

**Дешёвая проверка**: взять **только** подмножество hard+extra из уже
имеющихся 200 примеров (по нашему распределению — около 60 штук) →
сравнить прямую генерацию vs декомпозицию именно на них. Если прирост
скромный — не оправдывает сложность реализации, останавливаемся здесь,
не масштабируем.

---

## Ветка 5 — Schema linking (сокращение схемы до релевантных таблиц) — низкий приоритет

**Находка из литературы**: одна из работ (SQL-to-Schema, сравнение с
C3/DIN-SQL/RESDSQL) сообщает **скромный** эффект — прирост EX всего
0.001-0.01 от одного только schema linking.

**Вывод**: вероятно, не стоит усилий на реализацию **отдельно** от
других техник — эффект слишком мал относительно сложности. Не
приоритет, разве что как побочный эффект уже применяемого минифицированного DDL (который мы и так делаем).

---

## Итоговый порядок действий

1. Дождаться результата продолженного обучения (Ветка 1) — уже идёт
2. **Реализовать и дёшево проверить Ветку 2** (самокоррекция) — код готовлю сейчас
3. По результатам Ветки 2 — решить, стоит ли переходить к Ветке 3 (few-shot)
4. Ветка 4 (декомпозиция) — только если 2 и 3 не дают достаточного
   прироста именно на hard/extra
5. Ветка 5 — не приоритет, упомянута для полноты обзора

Такой порядок — от дешёвого к дорогому, от простого к сложному — и есть
ответ на ваш вопрос "как показать зрелый подход": не перебор наугад, а
приоритизация по (ожидаемая польза) / (стоимость проверки).
