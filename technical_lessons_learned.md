# Технические уроки — из работы над Customer Support Agent

Реальные проблемы, с которыми столкнулись при разработке через связку
чат + локальное выполнение (Windows/PowerShell/PyCharm), и как их избегать
заранее в следующем проекте.

## 1. Замена файлов — самая частая, самая дорогая по времени проблема

**Что происходило**: скачанный обновлённый файл не заменял старый (оставался
в другой папке, или под другим именем), скрипт запускался снова в старой
версии — часами позже находили несоответствие по косвенным признакам
(например, print-сообщения на не том языке).

**Как избегать**:
- После каждой замены файла — **сразу** проверять первую строку/docstring
  командой типа `Get-Content файл.py -TotalCount 5`, не полагаться на
  визуальное «я вроде скачал»
- Предпочитать **прямую вставку кода** в уже открытый в редакторе файл
  (`Ctrl+A` → удалить → вставить) вместо скачивания+переименования+
  перемещения — три отдельных шага, любой из которых может сорваться

## 2. PowerShell — не Unix-подобный терминал, синтаксис отличается

- `curl` в PowerShell — это алиас `Invoke-WebRequest`, **не** настоящий curl;
  флаги `-H`, `-d` не работают так же. Использовать `Invoke-RestMethod` с
  именованными параметрами (`-Method`, `-ContentType`, `-Body`)
- Переменные окружения (`$env:VAR=...`) действуют **только в том окне
  терминала**, где заданы — новое окно/вкладка не наследует их
- Если терминал завис (переменная в состоянии `>>`) — `Ctrl+C`, либо
  закрыть вкладку и открыть новую, не пытаться «долечить» зависшую сессию

## 3. Внешнее вмешательство между запусками отдельных скриптов

**Что происходило**: файл, правильно сохранённый одним скриптом,
оказывался откаченным к старому состоянию к моменту запуска следующего
скрипта (подтверждённая причина — реальный антивирус, скорее всего
блокирующий/пересканирующий свежесозданные файлы).

**Как избегать**:
- Добавить папку проекта в исключения антивируса **в начале работы**, не
  когда проблема уже проявилась несколько раз
- Если проблема всё равно возникает — объединять зависимые шаги в **один
  непрерывный запуск** одного скрипта, а не полагаться на то, что файл
  переживёт паузу между двумя отдельными запусками
- Защитное самоисправление внутри кода (например, нормализация значений
  сразу после загрузки, независимо от того, в каком состоянии их оставил
  предыдущий шаг) — рабочий обходной путь, если корень проблемы неясен

## 4. API-ключи — обращаться с осторожностью, даже в разговоре с Claude

- Никогда не вставлять сам ключ в чат — ни целиком, ни даже частично, если
  можно избежать (использовать проверки вида `$env:KEY.Length` или
  сравнение half-to-half вместо показа значения)
- Если ключ всё же случайно попал в чат — считать его скомпрометированным,
  сразу отозвать/удалить в консоли провайдера и создать новый
- Хранить ключ в отдельном локальном файле (не в папке проекта, не в git),
  копировать оттуда при необходимости

## 5. Бесплатные API-лимиты — узнавать заранее, закладывать время на них

- Многие сервисы (Voyage AI и подобные) дают **сильно урезанный** лимит
  запросов в минуту, пока не привязана платёжная карта — даже если сам
  токен-лимит остаётся бесплатным
- Скрипты с внешними API должны с самого начала включать повторные
  попытки (retry) с нарастающей паузой — не добавлять это задним числом
  после первого сбоя

## 6. Разметка через LLM (weak supervision) — числа, не текст, в качестве меток

- При батч-разметке через API просить у модели **номер категории**, а не
  текст названия — исключает риск, что модель случайно исказит/
  транслитерирует текстовую метку
- Обязательно `temperature=0` для детерминированности
- Проверять результат на небольшой выборке (сравнение с альтернативным,
  более дешёвым методом) перед тем, как полагаться на разметку всего датасета

## 7. Организация файлов — с первого дня, не в конце

- `git init` и структура папок (`data_pipeline/`, `training/` и т.д.) —
  до первой строчки кода, не после недели накопления файлов в одной
  плоской папке
- Чёткое разделение «финальный пайплайн» vs «черновые эксперименты»
  (например, папка `archive/` с самого начала) — экономит часы наведения
  порядка перед публикацией

## 8. Claude Code — реальные риски зависания и правила восстановления

**Что происходило**: интерфейс чата Claude Code дважды зависал (нет
курсора, не мигает индикатор) во время задач, связанных со скачиванием
файлов через внешние инструменты (`gdown`). Оба раза зависанию
предшествовало странное сообщение вроде «Unknown skill». Причинно-
следственная связь **не доказана окончательно**, но совпадение по
времени дважды подряд — не случайность.

**Как восстанавливаться, не теряя работу**:
- Файлы, уже записанные Code на диск, **не пропадают** при зависании
  интерфейса — зависает только сам чат-процесс, не файловая система
- Восстановление: `Get-Process | Where-Object {$_.ProcessName -like "*claude*"}`
  → `Stop-Process -Name "claude" -Force` → закрыть окно → новое окно →
  `claude --resume` в той же папке (сохраняет историю разговора)
- Если решено отказаться от Code полностью: `claude uninstall` (если
  установлен нативно, не через npm) — выбрать «Remove everything» для
  полной чистки, это не затрагивает веб-версию Claude в браузере, только
  локальный инструмент

**Более фундаментальный урок**: Code должен **останавливаться на каждой
согласованной вехе** и не продолжать самостоятельно (см.
`code_brief_template.md`). В реальности это правило было нарушено — Code
продолжил работу за пределы первой вехи без остановки, создав
незапланированный модуль. Это не привело к плохому коду (после проверки
код оказался качественным), но само нарушение договорённости — реальный
риск, который стоит явно проговаривать в начале каждой новой сессии.

## 9. Передача кода в Colab — GitHub надёжнее вставки текста

**Что происходило**: попытки передать код в Colab через вставку длинного
текста в буфер обмена (сырой код, base64 одной строкой, base64 по частям)
**трижды** приводили к повреждению данных при вставке (`BadZipFile`,
`negative seek value`) — конкретная причина повреждения (буфер обмена
браузера? редактор ячейки Colab?) не установлена, но сам факт
ненадёжности — подтверждён многократно.

**Что сработало стабильно**:
- **GitHub как промежуточное звено**: загрузить файлы на GitHub через
  обычный веб-интерфейс (Add file → Upload files) → в Colab один `git
  clone` → готово. Это использует три независимых, каждый раз надёжных
  механизма (обычное скачивание файла, обычная загрузка на сайт, сетевой
  `git clone`) вместо одного ненадёжного (вставка длинного текста)
- Прямая **бинарная** загрузка файла через кнопку в Colab (📁 → upload)
  тоже надёжна — в отличие от вставки текста, это не проходит через
  текстовый буфер обмена браузера

**Практический вывод**: для файлов **до пары КБ** вставка текста в
ячейку обычно работает нормально. Для чего-то большего — сразу
использовать GitHub, не тратить время на попытки с текстом.

## 10. Создание файлов в правильной папке на GitHub — частая ручная ошибка

При создании файла через «Add file → Create new file» **находясь не
внутри нужной папки**, легко случайно продублировать путь (например,
получить `src/src__init__.py` вместо `src/__init__.py`, или файлы
оказываются в корне репозитория вместо `src/`).

**Как избегать**: сначала **зайти внутрь** нужной папки (кликнуть на её
название в списке файлов), и только **находясь внутри неё** нажимать
«Add file» — тогда путь подставляется автоматически, конфликт исключён
структурно, а не полагается на аккуратность ручного ввода.

**Если ошибка всё же случилась** (файлы оказались не в той папке) — не
нужно пересоздавать репозиторий с нуля. После `git clone` можно
переместить файлы в правильную структуру локально, прямо в Colab:
`!mkdir -p src && !mv file1.py file2.py ... src/`.

## 11. Google Colab — смена типа среды выполнения стирает ВСЁ

**Подтверждено на практике, не предположение**: `Runtime → Change
runtime type` (например, включение GPU) **полностью пересоздаёт**
виртуальную машину — это стирает не только переменные в памяти, но и
**все файлы на диске**, установленные библиотеки, скачанные данные.

**Практическое следствие — порядок действий**:
1. Сначала всё, что НЕ требует GPU: установка библиотек, скачивание
   данных, получение кода (эти шаги одинаково работают на CPU-машине)
2. GPU подключать **в самую последнюю очередь**, непосредственно перед
   шагом, которому он действительно нужен
3. Если всё же нужно сменить тип среды **после** того, как что-то уже
   установлено — быть готовым повторить все предыдущие шаги заново, это
   не опция, а гарантированная необходимость

## 12. Долгие задачи (обучение модели) — монтировать Google Drive заранее

Инференс (генерация ответов уже готовой моделью) на 200 примерах занимает
секунды-минуты — потеря сессии не критична. **Обучение (fine-tuning)
занимает 20-60+ минут** — потеря сессии без сохранения чекпоинтов
означает потерю всего процесса целиком.

**Правило**: перед любым шагом длительностью больше нескольких минут —
сначала `drive.mount('/content/drive')`, сохранять промежуточные
результаты туда по ходу (не только в конце), не полагаться на то, что
сессия доживёт до конца без вмешательства.

## 13. При признаках путаницы — проверять текущее состояние командой, не памятью

Несколько раз за ночь предположения о том, «что уже установлено/скачано»
(основанные на более ранних сообщениях в разговоре) оказывались неверными
из-за скрытого сброса сессии. Единственный надёжный способ —
**каждый раз перепроверять реальное состояние** прямой командой (`!ls`,
`!nvidia-smi`, `!pip show <пакет>`) перед тем как продолжать, а не
полагаться на память о том, что было пройдено раньше в разговоре.

## 14. Письменный, обновляемый чек-лист — не роскошь, а необходимость

Ведение отдельного файла с пронумерованными шагами и чекбоксами
(`[x]`/`[ ]`), обновляемого после каждого подтверждённого шага, оказалось
критичным для восстановления порядка после нескольких сбросов сессии
подряд. Без него отследить, что реально уже сделано в **этой конкретной**
сессии (в отличие от более ранних, стёртых), было бы практически
невозможно.

## 15. Запуск скрипта из подпапки не видит соседний модуль — нужен PYTHONPATH

**Что происходило**: `scripts/evaluate_baseline.py` (лежал прямо в
`/content/`, рядом с `src/`) успешно импортировал `from src.dataset
import ...` без проблем. Но `scripts/train.py` (лежит **внутри**
`scripts/`, а `src/` — папка-сосед уровнем выше, не вложенная в
`scripts/`) упал с `ModuleNotFoundError: No module named 'src'`.

**Причина**: Python по умолчанию ищет импортируемые модули относительно
папки **самого запускаемого файла**, а не текущей рабочей директории
терминала. Когда скрипт лежит на одном уровне с `src/` — всё работает
само собой. Как только скрипт переносится в подпапку (`scripts/`), эта
папка-сосед перестаёт быть видна автоматически.

**Решение**: явно указать Python дополнительный путь поиска модулей
через переменную окружения перед запуском:
```bash
!PYTHONPATH=/content python scripts/train.py
```
(`/content` — путь к папке, где лежит `src/`; менять под конкретный
проект)

**На будущее**: закладывать этот момент в `RUNBOOK.md` заранее для
**любого** скрипта, который по структуре репозитория будет запускаться
не из той же папки, где лежит импортируемый пакет — не дожидаться, пока
это всплывёт как ошибка в момент реального запуска.

## 16. Unsloth + встроенные периодические чекпоинты HF Trainer — известный конфликт

**Что происходило**: реальное обучение (QLoRA через Unsloth) успешно
дошло до первого автоматического сохранения чекпоинта (шаг 50 из 5250,
`TrainingArguments(save_steps=50)`) и упало с:
```
_pickle.PicklingError: Can't pickle <class 'trl.trainer.sft_config.SFTConfig'>:
it's not the same object as trl.trainer.sft_config.SFTConfig
```

**Причина**: динамическая система патчинга/компиляции классов Unsloth
(`unsloth_compiled_cache`) создаёт версию класса `SFTConfig`, которую
модуль `pickle` считает технически «другим» классом, несмотря на
одинаковое имя и путь модуля — стандартный механизм HF Trainer пытается
сериализовать **весь** объект конфигурации обучения при каждом
автоматическом чекпоинте (`torch.save(self.args, ...)`), и падает именно
на этом шаге. Само обучение (loss, forward/backward pass) при этом
работает нормально — ломается только сохранение.

**Решение** — не использовать `trainer.save_model()` **вообще**, даже
вручную: этот метод внутри всегда вызывает `Trainer._save()`, который
**безусловно** пытается сериализовать весь объект `TrainingArguments` —
неважно, вызван ли он через автоматический `save_steps`, или вручную из
своего кода (первая попытка исправления через `save_strategy="no"` +
ручной вызов `trainer.save_model()` **не помогла** по этой причине).
Правильное решение — сохранять веса **напрямую через саму модель**,
минуя `Trainer` полностью: `model.save_pretrained(path)` +
`tokenizer.save_pretrained(path)`. Это использует собственный метод
сохранения PEFT/adapter-модели, который не имеет отношения к
`Trainer._save()` и никогда не трогает объект конфигурации обучения.

**На будущее**: при использовании Unsloth — по умолчанию не полагаться
на встроенное автосохранение `Trainer`, сразу закладывать периодическое
сохранение через явный колбэк с `save_model()`, не дожидаться, пока это
всплывёт как сбой на первом же реальном прогоне.

## 17. Дневной лимит GPU в бесплатном Colab — реальный, непредсказуемый по времени

**Что происходило**: после ~2.5 часов непрерывного использования GPU в
течение дня (включая несколько более коротких сессий раньше) — новая
попытка подключить GPU выдала: *«Cannot connect to GPU backend due to
usage limits»* — не «слишком много сеансов» (это другая, более лёгкая
проблема, решается через Manage sessions), а именно исчерпание дневного
лимита использования.

**Важно — Google сознательно не публикует точные цифры лимита** (прямая
цитата из их официального FAQ: лимиты «варьируются со временем», это
частично объясняется тем, что Colab и так предоставляет мощности
бесплатно). Реальные отчёты пользователей (GitHub issues, включая
подписчиков платного Colab Pro/Pro+) расходятся очень широко — от
«обычно 12-24 часа» до отдельных случаев в несколько дней ожидания.

**Практический вывод**:
- Не рассчитывать на фиксированное время восстановления при
  планировании работы — закладывать as честный риск, а не досадную
  случайность
- Разумно тратить GPU-время экономно с самого начала (см. раздел про
  порядок GPU в последнюю очередь — эта рекомендация становится ещё
  важнее с учётом дневного лимита, не только риска сброса сессии)
- Если сроки поджимают — Colab Pro снимает это ограничение практически
  сразу, разумная опция при недоступности бесплатного лимита
- Признак именно ЭТОЙ проблемы (не «много сеансов») — сообщение
  содержит явно фразу «usage limits», а не «too many sessions» —
  различать эти два сообщения, у них разные решения

## 18. Незакрытый инцидент — длительное «зависание» интерфейса чата (~2.5 часа), причина не установлена

**Что произошло**: во время работы над Вехой 2 интерфейс чата (не
Claude Code, не Colab — сам чат на claude.ai) не отвечал примерно 2,5
часа (не было курсора, не было индикатора активности). Разрешилось
само собой, без явного вмешательства.

**Честно — причина не подтверждена.** Рассматривались две версии:
(1) долгая отрисовка страницы браузером из-за большого объёма
накопленных вложений в разговоре (правдоподобно для секунд/минут, но
сомнительно для 2,5 часов), (2) реальный сбой на стороне интерфейса.
Ни одна версия не подтверждена достоверно.

**Практический вывод, не зависящий от причины**: это ещё один довод в
пользу вынесения критичной информации в **письменные файлы**
(чек-листы, RUNBOOK), а не в саму историю разговора — именно эта
практика позволила без потерь продолжить работу после инцидента. Если
разговор становится очень длинным и тяжёлым (много объёмных вложений) —
разумно начинать новый разговор внутри того же Project, ссылаясь на
актуальные файлы, а не продолжать бесконечно растущий тред.
